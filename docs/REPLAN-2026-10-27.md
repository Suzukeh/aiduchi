この文書を次の設計議論の入口とする。旧設計や過去の「完了」報告を、そのまま製品の合格判定に使わない。今回は調査・隔離テスト・文書更新のみで、アプリコード、既存データ、公開設定は変更していない。

## 1. 何を作るのか

**複数人が、動いているWebアプリを見ながら、AIと変更を作り、比較・検証して採用できる、自ホスト可能な開発ワークスペース。**

### ユーザーから確認できている要件

- aiduchiは汎用の共同バイブコーディング基盤。開発対象のソフトウェアは別リポジトリに置く。
- gehditorは開発対象の一つ。対象アプリの固有機能・データ型・仮組みをaiduchiに混ぜない。
- フローティングチャットを複数開ける。
- 「1チャット＝1進捗点」として関係をツリー／リストで追える。
- 編集参加時に表示名を決められる。
- AIはホスト提供が既定。個人のAPI設定を使うBYOKも選択肢として残す。
- GitHubで公開する。通常のWeb配信で使え、この環境ではCloudflare Tunnelを利用する。
- 運用コストを抑える。APIキーなどの秘密を共有リポジトリに入れない。
- 引き継ぎ文書を維持する。後方互換性に合わせて新設計を曲げる必要はない。

### 今回の提案であり、まだ合意していないこと

- 「1チャット」を、1メッセージではなく**一つの作業を相談・実行する会話スレッド**とする。
- 一つの進捗点には会話履歴と複数のチェックポイントを持たせる。送信のたびに別の作業カードへ移動しない。
- 窓の配置・前面化・閉じる操作は個人設定にする。共有するのは作業と成果であり、他人の机の配置ではない。
- 画面中央は動くアプリのプレビューとし、ファイル／差分へ切り替えられるようにする。

この作業単位と画面構成を確認してから、実装再開を判断する。

## 3. 目指す一連の操作

1. ホストが許可した対象リポジトリをプロジェクトとして登録する。
2. 参加者が名前を設定して入室する。名前と認証・権限は別の情報として扱う。
3. 採用済みの版がプレビューに表示され、表示中の版が分かる。
4. その版から「作業A」のチャットを開き、相談・指示する。相談だけならファイル変更は発生しない。
5. 実行を開始すると、分離した作業場所でAIがコードを変更する。進捗・ログ・停止ボタンを表示する。
6. 結果にコード差分、実行結果、プレビューを付ける。成功・失敗・未検証を区別する。
7. 別の参加者は同じ会話へ参加でき、または同じ基点から「作業B」を分岐して比較できる。
8. 権限のある参加者が変更を採用する。採用先が進んでいれば統合・再検証が必要で、後勝ちで上書きしない。
9. 採用後の版をGitに記録する。GitHubへのpush／PRと、実行中アプリの本公開は別の明示操作にする。
10. 閉じる・再読込・再接続で会話、確定した成果、実行状態を失わない。

最初の通し検証には小さな汎用Webアプリを使う。ダミーがMarkdownを一枚返しただけでは、この操作が完成したとは判定しない。

- 窓ごとに作業名・基点の版・実行状態を表示する。プレビューは明示的な操作で切り替え、他人の操作で勝手に切り替わらない。
- 共有する会話本文と、個人の未送信入力・配置を分ける。画面追従は必要になれば明示的な任意機能にする。
- 最初はリスト＋ツリー。Boardを含む三つの一覧を同時に作り込まない。
- 小画面では窓をタブ／ドック表示に寄せる。最初の受け入れ対象はデスクトップブラウザと明示し、スマホ対応を済んだことにしない。

## 5. 既存サービスから何を借りるか

2026-10-27に以下の一次資料を確認した。説明された機能の調査であり、各サービスのアカウントにログインして実操作した結果ではない。

- **Replit Task board**: 作業をDrafts／Active／Ready／Doneに分け、作業ごとの分離したコピーから、ログ・テスト・プレビューを確認して適用する。[1] 借りるのは「作業の生成」と「本線への採用」を分ける考え方であり、Boardそのものを必須にはしない。
- **v0 GitHub連携**: チャットの基点となるブランチと変更先の作業ブランチを区別し、PRを介する流れを用意している。[2] aiduchiでも会話だけでなく対象リポジトリの版と結びつける。
- **v0 Code viewer／Design mode**: プレビューからコードへ移れ、コードの手動編集と保存、プレビュー上の要素選択からの調整がある。[3][7] 最初はプレビュー／ファイル／差分の切替までとし、要素クリックによる自然言語修正は後段にする。
- **v0 Sandbox**: VM-backed chatでは実行環境が会話ごとに分離され、プレビュー・ログ／端末・コード表示が結びついている。[8] 商用基盤の採用ではなく、「動く成果を見せるための実行環境が必要」という設計上の参考とする。

## 6. データと同期の設計案

### 概念を分ける

| 概念 | 責任 |
|---|---|
| Project | 対象Gitリポジトリ、採用先、権限、実行設定 |
| Task / Chat | 一つの作業と会話履歴。ユーザーに見せる進捗点 |
| Run | 一回のAI実行。基点、モデル、状態、費用、ログ、キャンセル |
| Checkpoint | 確定したコードの版と、その版に対する検証結果 |
| Workspace | ある作業の編集中データと実行用ファイルの管理単位 |
| Window | 個人の表示。Taskへの参照と配置だけ |

進捗点の親子関係とGitの履歴は同一視しない。作業の分岐元・依存関係・採用先を別に記録する。UIはまずツリーとリストで見せ、統合が発生した場合はその関連も表現する。

### 何をどこに保存するか

- **Git**: 確定したコードと履歴。作業ごとのworktreeを候補とする。Git worktreeは同じリポジトリで複数の作業ツリーを持てる。[4]
- **SQLite**: プロジェクト、会話、作業、Run、イベント、Git版への参照、検証結果、権限、利用量。
- **Yjs**: 同じ作業場所の編集中ファイル。Y.Docの更新はトランザクションと更新イベントで扱える。[5] ただし、それを使うだけで作業の分岐やGitの統合が正しくなるとは仮定しない。
- **個人の表示状態**: 窓配置、前面順、選択中の版、未送信入力。共有ドキュメントには混ぜない。

共同編集のドキュメントIDにはproject／workspace／世代を含める。部屋とパスだけで別分岐を同じY.Textにつながない。初期化はサーバ側で一度だけ行い、空文字を「未初期化」と見なさない。Hocuspocusの永続化資料も、保存したYjsバイナリを復元し、新しい履歴を作り直さないよう注意している。[6]

### 人とAIの同時更新

最初から、同じファイルに人とAIが無制御で書く構成にしない。

1. 同じWorkspaceの共同編集はYjs経由で行う。
2. Run開始時に編集状態を確定し、その基点の版を固定する。
3. 最初の実装では、そのWorkspaceを実行中は読み取り専用にする。会話・別作業は続けられる。
4. AI結果は候補の版として保存し、検証してから反映する。切断・キャンセル・失敗時にも編集権の状態が復旧する設計にする。
5. 将来、編集中にもAIを走らせる場合は別Workspaceからの提案として扱い、基点の変化を検出して統合する。

確定したCheckpointは読み取り専用。編集するなら新しいWorkspace／版を作る。過去の版を開いただけで現在の共同編集中データを上書きしない。

### 採用と障害復旧

- 採用はstatusの付替えではなく、採用先の現版を検査したうえでのGit変更の統合と再検証。
- 既に採用された過去の事実は残し、「現在の採用版」の参照だけを進める。
- 採用先が更新されていたら競合として止める。無言の全ファイル上書きや自動force pushはしない。
- リクエストIDで二重送信による重複Runを防ぐ。再接続はイベントの再取得であり、AI再実行ではない。
- Git操作とDB更新は一つのDBトランザクションにはならない。処理段階を記録し、中断後に整合を確認できるようにする。
- サーバ再起動後、実行の生存が確認できないRunを「実行中」のまま放置せず、中断／要再開として示す。

## 7. 実行基盤・ライブラリ・費用

- React／TypeScriptを候補として維持する。現行のreact-rnd、React Flow、CodeMirrorも操作試験を通る部分は再利用できる。ただし現行storeの共有範囲やライフサイクルは継承しない。
- 同期は少人数の自ホストYjs＋Hocuspocus、保存はSQLiteを第一候補とする。追加SaaS契約なしの構成を目標にするが、電気・ホスト資源・保守・AI利用を含め「無料」と断定しない。
- 複数チャット窓と、AIの複数同時実行は別。最初はAI実行枠を一つに制限して待ち行列を表示し、実測後に増やす。
- この環境のオーケストレーション正本はPaseo daemon。独立したCLI委譲経路は追加しない。aiduchiからは認証されたサーバ側の限定操作を通じて接続する案とする。
- **Paseo接続、必要なモデル／個人資格情報の選択、作業領域の制限、実行隔離は未検証。ここを最初の技術試験の合否判定にする。** 未確認のAPIや安全性を前提に本実装を進めない。
- 生成アプリのインストール／ビルド／起動はホストの普段の作業環境から隔離する。worktreeの分離だけを実行隔離とみなさない。コンテナ等の具体方式は技術試験で決める。
- LLMからJSONを受け取るだけの自作処理を、完成したコーディングエージェントの代わりにしない。

## 8. 機密・権限・公開

- 表示名、参加認証、閲覧／編集／採用権限を別にする。APIと同期の両方で権限を検査する。
- ホストキーはサーバ側のみ。実行する生成アプリ、プレビュー、会話、ログへ渡さない。
- BYOKは任意。既定ではブラウザのメモリにのみ保持し、サーバへ渡る方式ならその事実を表示する。localStorageへ自動保存しない。永続保存を導入する場合は別途設計・同意する。
- 認証情報の参照と非機密設定を分ける。キー失効・再入力の導線を用意する。BYOK失敗時にホスト課金へ無言で切り替えない。
- プロバイダURLを無制限に利用者指定させない。ホストが許可した接続先を使用する。
- 利用制限はroomだけでなくホスト／プロジェクト／参加者／Runに設ける。実行前の予算予約、出力・時間・同時実行の制限を用意する。
- 招待情報は期限・失効を持たせ、参加後はセッションへ交換する。長期の共有秘密をURLクエリに残す設計を廃止する。
- プレビューを制御画面と別オリジンに隔離し、ホスト専用Cookie、Origin検査、CSRF対策、iframe権限を設計する。生成アプリから制御APIや秘密へ到達できないことを試験する。
- 生成物の実行には対象リポジトリ以外のホーム、資格情報、管理ソケットを渡さない。資源とネットワークも制限する。
- Tunnelは公開経路の選択肢であり認証の代わりではない。アプリの権限確認と公開の合否判定を別にする。
- ホストAI未設定時は「未設定」と表示する。dummyは明示したテスト／デモ専用にし、実AI成功と同じ表示をしない。
- 初期対象は信頼できる少人数の招待制。不特定多数が任意コードを実行できるサービスは今回のMVP外。

## 9. 実装順と、次へ進める条件

日数の約束ではなく、ユーザー操作が成立したことを次の段階へ進む条件にする。各段階の完了は全体完成を意味しない。

| 段階 | 作るもの | 次へ進める条件 |
|---|---|---|
| 0: 要件・操作の合意 | この計画と、承認後のクリック可能な画面試作 | 複数窓、作業の分岐、プレビュー比較、採用の意味をユーザーが確認。モックはモックと表示 |
| 1: 実行経路の技術試験 | 許可した汎用サンプルの分離作業領域、Paseo接続、起動・停止・検証 | 秘密を渡さずコード変更→ビルド→実プレビュー→停止が可能。権限／資源の境界も確認 |
| 2: 一人で最後まで使える最小版 | 一つの作業会話、実AI、変更差分、プレビュー、採用・取り消し | 表示名、複数往復、失敗、停止、再読込を含めて実アプリの変更を確認。コードがGitに残る |
| 3: 複数人・複数作業 | 独立した窓、共有会話、分岐、採用競合 | 二人が別作業を進めても入力・表示・成果を奪わない。同時採用で上書きしない |
| 4: 同じファイルの共同編集 | Workspace単位Yjs、保存、世代切替、再接続 | 同時入力、全文削除、ファイル切替、分岐切替、再起動で内容を保持し、別分岐に混ぜない |
| 5: 配布・実用投入 | BYOK、権限制御の仕上げ、起動／停止手順、Tunnel越し試験 | 別環境で再現可能。二人の通し操作、権限拒否、費用制限、秘密分離を実際に検証 |

Phase 1で隔離やPaseo接続が成立しなければ、制約と代替案を提示して計画を修正する。UIやREADMEで「対応済み」として先に進めない。

## 10. 受け入れ試験の基準

- 入力中に他人が操作してもフォーカスと未送信文が失われない。最小化・再表示でも保持する。
- 編集を開始するだけでは内容が変化しない。意図的な空ファイルと未初期化を区別する。
- 複数ファイルの編集を保存し、再読込して同じ内容になる。元のCheckpointは不変。
- 分岐A／Bに同名ファイルを置き、別内容を維持できる。同じWorkspaceだけが共同編集される。
- 「質問だけ」「計画」「実行」「追加修正」を区別でき、会話履歴が必要な文脈として使われる。
- 二重送信、AI失敗、停止、通信切断、サーバ再起動を再現し、重複実行や永久の実行中状態を残さない。
- プレビューとテスト結果に版を付け、別版の成功を現在の版の成功として見せない。
- 採用競合を意図的に作り、上書きではなく競合として検出する。
- 未認証／閲覧者による編集・実行・採用を拒否する。予算超過時も実行しない。
- 画面・配信JS・ストレージ・ログ・生成アプリにホスト秘密がないことを確認する。
- 決定的なスタブによる自動テストと、予算を決めた実AI・実リポジトリの通し試験を分けて記録する。
- 「8本成功」のような本数だけで完成判定しない。要求した操作とデータ保持を一つずつ検証し、未検証は未検証のまま残す。

## 11. 今回しないこと

アプリの書換え、既存DBの削除・移行、プロセスの停止・再起動、公開先の変更、AIキーの読出し、対象アプリへの機能追加は行わない。旧API／DB互換性を新設計の制約にはしないが、既存データを勝手に消してよいという意味でもない。

次の判断は、**作業スレッドを進捗点にすることと、プレビュー中心・複数チャット窓の画面構成への合意**。合意後も最初は画面試作と小さな技術試験であり、全面実装の自走には戻らない。
